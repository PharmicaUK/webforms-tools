# CLAUDE.md

Tooling for ASP.NET WebForms VB.NET Web Application Projects. .NET 10 / C#. See README.md for user docs
(designer generator, VB formatter, ASPX language server, editor packages).

## Layout

```
src/WebForms.Markup/      Markup tokenizer + tree builder (no dependencies; reused by the language server)
  MarkupTokenizer.cs        TemplateParser lexical rules: directives, <% %>, <%-- --%>, tags; positions
  MarkupDocument.cs         Builds the server-element tree. Only runat=server tags nest (plus whatever the
                            IMarkupSchema says are inner properties / collection items); literal same-name
                            tags are repeat-counted like ASP.NET does.
src/WebForms.Designer/    Designer generation
  ProjectContext.cs         .vbproj (RootNamespace, HintPaths, TargetFrameworkVersion), web.config <controls>,
                            virtual paths, reference-assembly lookup. CLI: cached per project directory
                            (ForFile). LSP: Create + Refresh (stamps of every file it read; clears caches or
                            says Reload).
  TypeSystem.cs             MetadataLoadContext over framework ref assemblies + project refs: ParseChildren,
                            ControlBuilder, ITemplate + TemplateInstance, collection item types, events.
                            Project refs are loaded from bytes (a mapped file is locked, see LSP findings).
  ControlTypeMembers.cs     Enumeration for completion: types per namespace, properties (settable / inner /
                            Content sub-properties, hyphen paths), events with args types, enum values.
  ControlSchema.cs          IMarkupSchema implementation: tag -> type resolution (asp:, Register, web.config,
                            user controls, HTML controls) and ControlBuilder decisions.
  CodeBehindScanner.cs      Small VB scanner (members + namespace of the code-behind class). Not Roslyn on
                            purpose: Roslyn costs 50-150 ms per process.
  DesignerGenerator.cs      Markup -> DesignerModel (class, namespace, fields, Master type) + diagnostics.
  DesignerWriter.cs         DesignerModel -> text; DesignerStyle (VS / Rider / detected from existing file).
  DesignerOutput.cs         Applies --style / --master against the existing file to get the bytes to write.
  ExistingDesigner.cs       Reads semantic content back out of an existing designer (any IDE).
src/WebForms.Formatting/  VB formatter (Roslyn Workspaces, pinned; compiled against Roslyn internals, see Rules)
  VbFormatter.cs            Keyword casing -> CodeCleaner token providers -> Formatter; refuses syntax errors.
  KeywordCasing.cs          Syntactic replacement for VS's case correction (keywords + setter `Value` only).
  GeneratedCode.cs          *.designer.vb / *.g.vb / <auto-generated> files are passed through.
src/WebForms.LanguageServer/  `webforms lsp` (hand-rolled LSP; System.Text.Json source-generated)
  Protocol/                 LspTypes.cs (the LSP subset used + JsonSerializerContext), JsonRpcConnection.cs
                            (Content-Length framing, serialized writes).
  WebFormsLanguageServer.cs Read loop (handles $/cancelRequest) + one handler loop, in order; lifecycle; dispatch.
  ServerSettings.cs         User settings: initializationOptions, then workspace/didChangeConfiguration.
  WebFormsWorkspace.cs      Open buffers (override disk), one ProjectContext per project (Refresh on every use),
                            analyses / parsed VB files cached by buffer version or file stamp.
  MarkupAnalysis.cs         DesignerGenerator run on the buffer text (same types as the designer) + hit testing.
  VbFile.cs                 Roslyn VB syntax tree (no compilation): methods, Handles, members, uses, FindControl.
  Navigator.cs              Definition / references: what is under the cursor (NavigationTarget) -> locations.
  MarkupDiagnostics.cs      Published diagnostics: the designer pipeline's (CLI codes), WF5001/WF5002 handlers, WF0100 stale designer.
  DesignerFiles.cs          "Generate designer" (command, code action, on save): DesignerOutput bytes written to disk.
  LineDiff.cs               Formatting result -> minimal whole-line TextEdits (Myers over lines).
  Completion/               MarkupCursor (what is being typed, tolerant of unfinished tags), CompletionProvider
                            (tags / attributes / values / directives from the metadata), XmlDocumentation (resolve),
                            ExpressionBuilderCompletion (<%$ AppSettings: / ConnectionStrings: / Resources: %>).
  CodeBlocks/               VB in markup code blocks: Projection (markup -> hidden VB class + block map),
                            VbProjectFile (.vbproj Compile items / refs / options), CodeBlockProject (one Roslyn
                            solution per project, built in the background), CodeBlockService (completion, Eval
                            fields, hover, definition, references, BC errors; mapped back to markup).
src/WebForms.Cli/         `webforms` dotnet tool (PackageId Pharmica.WebForms.Tools). Program.cs (args, exit codes),
                          FormatCommand.cs (`webforms format`), LspCommand.cs (`webforms lsp`),
                          ClaudeHook.cs (`webforms hook claude`).
tools/CorpusReport/       Regression checks against a real WebForms solution (the "corpus"): designer report,
                          Roslyn cross-check of CodeBehindScanner, formatter check, language server check.
tests/WebForms.Tests/     xunit; Fixtures/SampleApp is a tiny synthetic WAP project.
editors/vscode/           VS Code extension: `aspx` language + TextMate grammar (syntaxes/), client
                          (src/extension.ts, vscode-languageclient, esbuild bundle), integration test (src/test/:
                          downloads VS Code, runs against the `webforms` on PATH).
editors/neovim/           README only: vim.lsp.config, conform.nvim and designer-on-save snippets.
editors/claude-code/      Claude Code plugin: .lsp.json (server), hooks/hooks.json (`webforms hook claude`).
.claude-plugin/           marketplace.json: this repo is the plugin's marketplace (`webforms@webforms-tools`).
.github/workflows/        ci.yml (build, format, test, pack, VS Code test); release.yml (on a `v*` tag: GitHub
                          Release with the nupkg and the .vsix; NuGet push when NUGET_API_KEY is set).
```

## Commands

```bash
dotnet build
dotnet test tests/WebForms.Tests
dotnet pack src/WebForms.Cli -c Release            # -> artifacts/nupkg/Pharmica.WebForms.Tools.<ver>.nupkg
cd editors/vscode && npm install && npm test        # VS Code integration test (needs the tool installed)
#   npm run package -> artifacts/vsix/webforms-<ver>.vsix
#   WEBFORMS_TEST_GRAMMAR_FILES="a.aspx;b.ascx" npm test: those files (e.g. pages of a real solution, opened
#   read-only) must have no invalid.illegal tokens; WEBFORMS_TEST_GRAMMAR_VERBOSE=1 prints the scopes around each
claude plugin validate --strict ./editors/claude-code && claude plugin validate --strict .
#   (ReadyToRun win-x64, UseAppHost=false; never --no-build: packing is a separate RID-specific build)
```

### Corpus checks

`tools/CorpusReport` runs against a real WebForms solution you have locally. The path is a required argument
(there is no default); it only reads the corpus and writes under `artifacts/corpus-report/`.

```bash
# Designer report: buckets exact / semantic (formatting only) / likely stale / unexplained / error
#   generated/: every regenerated designer, mirroring the corpus layout, for diffing
#   --filter <substring> limits to matching markup paths; exit code 1 if anything is unexplained or errored
dotnet run --project tools/CorpusReport -- <corpus>

# Check the light VB scanner against Roslyn on every class in every .vb file of the corpus
dotnet run --project tools/CorpusReport -- <corpus> --verify-scanner

# Run the formatter over every .vb file of the corpus: no exceptions, idempotent, --lines 1-N == whole file,
# token stream unchanged apart from case / Then / Case / () / : / modifier order / literal spelling; a middle --lines range
# changes nothing after it (before it: whitespace and `_` only); the LSP's line edits rebuild each result exactly.
# Formatted copies of changed files go to artifacts/corpus-report/formatted/. Exit 1 on any problem.
dotnet run --project tools/CorpusReport -- <corpus> --verify-formatter

# Run the language server in process over every markup file (read-only): every event attribute must reach its
# handler, every designer-field ID its field; completion at every tag, property / event attribute, handler and
# enum value must offer it; `</` at every server end tag must name its element; diagnostics are counted by code;
# every code block is compiled (BC errors listed, member completion after each `x.` (again with the block
# unclosed) and `Eval("` fields checked); times a keystroke on the 3 largest pages. Misses in
# artifacts/corpus-report/lsp.md. Exit 1 on any exception.
dotnet run --project tools/CorpusReport -- <corpus> --verify-lsp
```

Run the first two after any change to the parser, schema, scanner or writer, `--verify-formatter` after any
change to WebForms.Formatting or the Roslyn version, and `--verify-lsp` after any change to
WebForms.LanguageServer, the parser or the schema. Keep the baseline of your corpus outside the repo and compare
before / after (timings against `main` in the same session: they vary with machine load). A healthy run: 0
unexplained designers and 0 errors (every semantic / likely-stale one checked by hand); 0 scanner mismatches; 0
formatter problems (files with real syntax errors are refused, which is correct); no LSP exceptions; 0 completions
not offered apart from the documented exclusions (HTML attributes such as `placeholder`, controls inside
`<!-- -->`, parameterless handlers); 0 Private / Friend / parameterless handlers offered; 0 BC errors in code
blocks of pages that compile in ASP.NET.

## Rules

- **Never write to the corpus.** The report writes only to `artifacts/`. For CLI experiments against it use
  `--stdout` or `--check`. Never copy names, paths or statistics from a private corpus into the repo.
- Ignore `.claude\worktrees\*`, `bin`, `obj` (obj holds AspnetCompileMerge copies of markup) in a corpus.
- Keep the CLI interface, exit codes (0/1/2/3) and the `file(line,col): error|warning CODE: message`
  format stable; Neovim, Claude hooks, MSBuild and CI depend on them.
- Output must be deterministic. It depends only on the markup, referenced markup (.ascx / .master Inherits),
  code-behind, project files, reference assemblies, and the existing designer (for style / Master preservation).
  `webforms format` output depends only on the input text and `--lines` (no project, no references).
- Unresolvable types are errors, never silent guesses.
- Bump `<Version>` in `src/WebForms.Cli/WebForms.Cli.csproj` with every change that ships (semver; while 0.x, a
  breaking CLI change bumps the minor), and keep `editors/vscode/package.json` and
  `editors/claude-code/.claude-plugin/plugin.json` at the same version. `dotnet tool update` only installs a
  higher version. A release is a `v<version>` tag (`.github/workflows/release.yml` checks they all match).
- Roslyn is pinned exactly (`[5.9.0]` in WebForms.Formatting.csproj). WebForms.Formatting uses Roslyn internals
  (`CodeCleaner`, `ICodeCleanupProvider`, `CodeCleanupOptions`) through Krafs.Publicizer, never reflection, so an
  incompatible upgrade fails the build. To upgrade: bump the pin, build, run `--verify-formatter` and the tests.
  History: `CodeCleaner` is unchanged 4.4-5.9; `GetCodeCleanupOptionsAsync` lost a parameter between 4.8 and 4.14.

## Designer findings (why the code is the way it is)

- Designer formatting differs by IDE/version, not semantics. See the README table. `--style auto` keeps it.
- The typed `Master` property (`Public Shadows ReadOnly Property Master()`) is added by Rider, never by Visual
  Studio (checked by saving a page in VS 2022, before and after a build). It causes bugs: it casts to the markup's
  master, and pages that set `MasterPageFile` in `Page_PreInit` then throw `InvalidCastException`. Default
  `--master directive` writes it only for `<%@ MasterType %>` (VS behaviour; required by code using `Master.X`)
  and removes Rider's; `--master keep` preserves it. The corpus report uses `keep` so that it still measures how
  faithfully the rest of each file is reproduced.
- The `Namespace` block shape was verified by saving a temporary namespaced page in VS 2022
  (`tests/WebForms.Tests/Fixtures/VisualStudio/Namespaced.aspx.designer.vb`): one blank line before
  `Namespace X` instead of two. VS also keeps the existing file's encoding (no BOM if the file had none), and does
  not create a missing designer on save, it only regenerates an existing one.
- Controls inside HTML comments get fields; inside `<%-- --%>` they don't.
- HtmlTable / HtmlTableRow are `ParseChildren(true, "Rows"/"Cells")`: `<tr>`/`<td>` inside a server table are
  collection items (controls even without runat). `HtmlTable.Rows` is `[IgnoreUnknownContent]`, so
  `<colgroup>`/`<thead>`/`<tbody>`/`<tfoot>` there are silently dropped (not rendered!) while the `<tr>`s inside
  them are still rows. `HtmlTableRow.Cells` has no such attribute: a non-cell tag in a server row is a real parse
  error.
- An `Inherits` that doesn't start with the project's RootNamespace: the designer namespace then follows the
  code-behind class, with warning WF1002.
- Existing designers are not all correct: they are regenerated only on save, by two IDEs, and sometimes edited by
  hand (fields appended out of document order, one-line `<summary>`, mixed whitespace, fields kept for controls
  removed from the markup). The corpus report therefore compares semantically and uses `git log` to classify a
  designer committed before its markup as "likely stale".

## Formatter findings

- VS pretty listing = VB `CommitFormatter` (Roslyn EditorFeatures, LineCommit/) = `CodeCleaner` with every default
  provider except Simplification, plus a format pass. All of that is `internal`; public `Formatter.FormatAsync` only
  does whitespace. The `End If`-on-Enter feature (EndConstructGeneration) needs a VS `ITextView`; the
  GenerateEndConstruct code fix inserts an empty block right after the `If`, so it is useless to a formatter.
- Identifier case correction (the CaseCorrection provider) binds against the compilation. On one file it re-cases
  wrongly (`LoginStatus.Success` -> `loginStatus.Success`: the enum is in another file so it binds the local;
  `.Key` -> `.key` on an unreferenced type). Even the whole project without HintPath references gets some
  wrong. Hence KeywordCasing (syntactic) instead; `value` in a setter is the only identifier it touches.
- AddMissingTokens leaves a zero-width whitespace trivia after the end-of-line of a statement it gave `()`; the
  formatter then inserts a blank line if a block statement (If/For/Try...) follows. VbFormatter strips those between
  the passes. Formatting the cleaned *text* instead of the tree is wrong: inserted tokens have no whitespace yet
  (`bOkThen`, `Select CaseverifyTwoFa`).
- `EndIf` is a syntax error (BC30826) that cleanup fixes, so "refuse on syntax errors" checks the *result* and
  reports the original errors whose ids are still present.
- Timing: ~400-550 ms per process with ReadyToRun (JIT: 700-970 ms; conform's default timeout is 1000 ms). A RID-
  specific tool package with an apphost installs a `.cmd` shim, which Git Bash and libuv can't run by bare name;
  `UseAppHost=false` keeps the `dotnet` runner and the `webforms.exe` shim. The language server serves formatting
  from a warm process instead.

## Language server findings

- Design: navigation from markup attributes, completion of handlers and the designer pipeline are syntactic /
  metadata-based (Roslyn syntax trees, no compilation), so they never wait. Code blocks need semantics, so each
  project with code blocks in an open file gets a full Roslyn compilation (CodeBlocks/). Measured on a ~500-file
  project with ~230 references: parse 0.12 s, full binding 1.0 s, ~120 MB managed / ~350 MB working set; with the
  CompletionService workspace ~140 MB / ~440 MB.
- Projection: block text is copied verbatim, so the source map is one (markup, projection, length) triple per block.
  `<% =x %>` is an expression (ASP.NET's regex is `<%\s*?=`). Template blocks go into one Sub per
  template with `Container As <[TemplateContainer] type>` (TypeSystem reads it; a GridView TemplateField's is
  `IDataItemContainer`) and `Item` / `BindItem` from the nearest `ItemType`. `Bind()` is compiler magic in ASP.NET:
  the projection declares a stub. The class is `Namespace Global.ASP` (as App_Web pages), inheriting the class the
  designer is generated for (root namespace + designer namespace + class), not the raw Inherits string. Project-level
  errors (build-generated files, a native DLL in bin, `My` extensions) are outside blocks and never reported; bin
  DLLs without metadata are skipped (BC31519 otherwise).
- Blocks being typed: Neovim doesn't close `<%`, and the tokenizer (like ASP.NET) runs an unfinished block on to the
  next `%>`, so the markup after the cursor became code (`Container.` + `<div` is a VB XML axis access: 0 items)
  and the template's end tag, or the rest of the tag around `Text='<%# x.'`, vanished from the tree (no `Container`
  / `Item` type). The tokenizer stays as it is (it is ASP.NET's behaviour, and the designer relies on it);
  `CodeBlockService` builds the projection from a copy with `%>` inserted where the unfinished block's code ends
  (`Projection.RepairPoint`: the first tag, or the value's closing quote when the block starts an attribute value,
  i.e. `="<%` or `='<%`; a block after a quote in client-script JSON is not one), and maps spans back.
  Requests in a block wait up to 5 s for the first build: an empty answer left blink's menu blank until the next key.
  `Eval("` without its closing quote: VB 14 strings span lines, so the string runs on through the projection and the
  tree shows no argument; the block's text before the cursor (`Eval("partial`) decides then.
- `Eval("Field")` is typed via `ctl.DataSource = <typed collection>` in the code-behind (a nested repeater without
  an ID must not borrow its parent's DataSource). A `DataTable` / `SqlDataReader` source stays late-bound.
- URIs: VS Code escapes the drive colon (`file:///c%3A/...`); `System.Uri.LocalPath` then keeps `/c:/...` and
  `GetFullPath` made it `C:\c:\...`. URIs go back to the client exactly as it sent them (`DocumentUri` remembers
  each): on Windows `GetFullPath` expands 8.3 names, so on a GitHub runner (`C:\Users\RUNNER~1\...` temp) the BC
  diagnostics were published for `C:\Users\runneradmin\...` and VS Code, which matches documents by URI string,
  never showed them.
- `MetadataLoadContext` memory-maps the assemblies it loads from a path, and a mapped file can't be overwritten on
  Windows ("being used by another process"). Harmless for the short-lived CLI, but a warm server would break every
  build that writes `bin\`. `TypeSystem` therefore loads project references with `LoadFromByteArray` (framework
  reference assemblies stay mapped: they never change). Covered by a test that rebuilds an assembly while the
  server holds it.
- WebForms code wires events mostly with `Handles` rather than markup attributes (`On<Event>=`), so "go to
  definition" on an ID lists the `Handles ID.Event` subs right after the designer field.
- Staleness is detected by stamping (mtime + length) every file a `ProjectContext` read, checked on each request,
  not by file-watch notifications: correct even when the editor sends none. web.config / referenced markup
  changes clear caches; `.vbproj`, a DLL or the `bin` directory listing changing recreates the context.
- Neovim (0.12): stock Neovim has no ASP.NET filetype (with `--clean`, `.aspx` was detected from its content as
  `mason`, HTML::Mason) and calls VB `vb`; the README snippet adds the filetypes itself and lists both `vb` and
  `vbnet`. `vim.lsp.config`'s `root_markers` takes names, not globs, hence the `root_dir` function for `*.vbproj`.
- Neovim logs anything a server writes to stderr at ERROR level, so `webforms lsp` writes nothing there unless
  something is really wrong (no banner; logging only with `--log`). Neovim starts one server per root, all with the
  same `--log` path: the log is opened shared and each line carries the pid (an exclusive open crashed the second
  server).
- Timing (stdio, packed ReadyToRun tool): first request in a project ~140 ms (metadata + Roslyn load; ~230 ms
  JIT), then ~8 ms on a page with a 2,500-line code-behind.
- Completion. Templates (`ItemTemplate`, `EmptyDataTemplate`, …) are `[Browsable(false)]` in System.Web
  (Visual Studio edits them in template mode), so the Browsable filter must not apply to inner (template /
  `PersistenceMode`) properties. Sub-properties are written to any depth (`HeaderStyle-Font-Bold`); completion
  offers two levels. `Font-Names` is a settable `string[]`: settable collections are attributes too. Attributes on
  server controls that are not properties (`class`, `placeholder`, `autocomplete`, `data-*`, `onclick`) are
  rendered as they are by ASP.NET, so they are not offered (the HTML server offers HTML attributes on every tag)
  and are not errors.
- Completion response size: a GridView's attribute list is 329 items. With the file path in every item's resolve
  data it was 145 KB; items now carry one integer (`data`, interned server-side) and, when the client advertises
  `completionList.itemDefaults: ["editRange"]`, `textEditText` with the range sent once: ~60 KB. The `textEdit` range
  is required (blink.cmp cannot work out a word that contains `:` or `-`).
- Handler completion. ASP.NET compiles the markup into a class that *inherits* the code-behind class, in
  another assembly (App_Web_*.dll), and wires `OnClick="x"` there: `Private` and `Friend` Subs are not accessible
  (`Protected Friend` is). Parameterless Subs are legal (relaxed delegates) but in a large code-behind dozens of
  helper Subs would qualify, so they need `completion.zeroArgHandlers`. Ranking alone doesn't help: blink / VS Code
  re-rank by fuzzy score once a prefix is typed. ASP.NET still parses server controls inside `<!-- -->` (they get
  designer fields), but completion is off there.
- `</` uses its own open-element stack over the tokens before the cursor, not the parsed tree (which pairs a
  new inner `<asp:Panel>` with the outer Panel's end tag below). No end tag closes across a server element: ASP.NET
  matches end tags against the innermost server element only (real pages have HTML unbalanced across `<% If %>`
  branches, and a stray `</div>` there would otherwise close `<div runat="server">` and the Panels inside it). In
  client `<script>` bodies only server tags count (a master page can have a ContentPlaceHolder in one).
- Keystroke cost on a 270 KB page: was ~26 ms, almost all re-analysis: tokenizing twice, and re-reading and
  re-scanning the 7,000-line code-behind on every edit. The generator now builds the tree from the directive pass's
  tokens and takes a code-behind scanner, which the workspace caches by buffer version / file stamp (the analysis
  cache key includes the code-behind's stamp): ~6 ms. Parsing a full-text `didChange` of that page is ~1 ms, so
  sync stays `Full`.
- Diagnostics are pushed for open markup files on open, on save and 300 ms after the last change to any
  buffer (a code-behind edit changes its markup's WF5001 / WF5002). The debounce timer only posts a tick into the
  message queue: all work stays on the one handler loop. Each publish recomputes every open markup file (analyses
  are cached) and sends only the files whose list changed. WF0100 compares the generated designer bytes with the
  file, only when the buffer equals the file on disk (newlines normalised: Neovim sends `\r\n` for `fileformat=dos`).
- "Generate designer" writes to disk (`DesignerFiles`), never `workspace/applyEdit` (that leaves an unsaved buffer
  in Neovim). Handler diagnostics skip classes that inherit a custom base class (it may declare the handler) and
  pages whose code-behind can't be found (e.g. `CodeBehind="~/..."`).
- Range formatting re-indented nothing on the first line of the range: Roslyn's formatter only touches token pairs
  inside the span, and the first line's indentation belongs to the pair (previous line's last token, first token).
  The format pass now starts at the end of the previous line. Comment lines directly above the range are leading
  trivia of its first token and get re-indented with it; cleanup already worked on whole statements (a multi-line
  statement running into the range loses its `_`). `--verify-formatter` checks a middle range for exactly that.
- Formatting from the server: first call ~0.6 s (Roslyn Workspaces + MEF), then ~25 ms for a typical code-behind,
  ~300 ms for a 7,000-line one. Results go out as Myers line-diff edits (a whole-document replacement
  drops Neovim's marks and folds). Formatting is registered dynamically for `**/*.vb` when the client supports it,
  else advertised statically with `null` for markup; the client's `languageId` is never used (Neovim sends `aspx`
  for .ascx / .master and `vbnet` for .vb).

## Editor package findings

- VS Code grammar: HTML (`text.html.basic`) with the server constructs injected (`L:` selector) everywhere except
  inside VB, so `<%# %>` in attribute values and client scripts is still VB (VS Code's own `source.asp.vb.net`). HTML
  marks what it doesn't know `invalid.illegal`: prefixed server tags (`asp:Button`) and inner properties (capitalised:
  `<ItemTemplate>`, `<Triggers>`) get their own tag rule; a self-closed `<div ... />` is fine. HTML tokenizes
  `onclick=` / `style=` values with one regex that stops at the first quote, which can be inside the VB
  (`f('<%= Session("A") %>')`), so a quoted value containing `<%` becomes a plain string with the blocks injected.
  What is still `invalid.illegal` in real pages is real markup quirks: XML feed pages, lowercase inner properties
  (`<headerstyle>`, `<contenttemplate>`), `<xml>`, `</input>`, a stray `</script>`, doubled quotes.
- `_workbench.captureSyntaxTokens` (what VS Code's colorization tests use) gives the scopes in the integration test.
  `@vscode/test-electron` downloads VS Code into `.vscode-test/`.
- Claude Code (tested headless with `claude -p --plugin-dir`): definition through the `LSP` tool, BC errors after an
  edit, designer regenerated by the hook, designer edit blocked. Diagnostics reach Claude right after the edit,
  before the PostToolUse hook regenerates the designer, so WF0100 showed up as a problem: the plugin sets
  `diagnostics.staleDesigner: false`. The hooks cost ~80 ms per Edit / Write (twice): the README suggests
  `--scope project`. `.lsp.json` and `lspServers` entries are strict (unknown key = plugin doesn't load) and
  `claude plugin validate` doesn't read `.lsp.json`.
